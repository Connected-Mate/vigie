Five watch posts, one report

A single lookout only sees one slope. Vigie cross-checks four public vulnerability databases, plus deps.dev for early signals, with no account and no key, and gives one answer sorted by urgency.

  • The smoke

    OSV.dev

    Known vulnerabilities and malicious packages in open source packages, matched on your exact version. Run by Google and OpenSSF, it gathers advisories from GitHub, PyPA, RustSec, Go and others.

  • The fire

    CISA KEV

    The catalogue of vulnerabilities already exploited in real attacks. If one of yours is in it, Vigie marks it “act now”.

  • The wind

    EPSS

    A score updated daily by FIRST.org: how likely a vulnerability is to be exploited soon. It tells you which way a fire might spread.

  • The regional bulletin

    CERT-FR

    The latest alerts and advisories from ANSSI, the French government agency. Recent bulletins only.

  • The forester’s notebook

    deps.dev

    Not vulnerabilities, signals: a version deprecated by its author, a version published in the last 3 days, and what an install pulls in. Asked when single packages are checked or installed, not for whole-project scans.

What the lookout actually does

It watches, it warns, it says where to go. Three ways in, one engine: tools for your agent, a hook, a command line.

  1. 01

    It stops the burning tree at the gate

    Before a command that installs or runs a package (npm, pnpm, yarn, bun, npx, pip, uv, poetry, cargo, go, gem, composer, dotnet), the hook works out the version it would really bring and checks it, along with what it pulls in. High-priority known vulnerability or malicious package: the command is blocked, and the agent gets the report and the fix.

  2. 02

    It scans the whole forest

    Give it a project folder: Vigie reads its dependency files (package-lock.json, uv.lock, Cargo.lock, go.mod and others, 19 formats in all), sub-folders included, and checks every version it finds. The hook runs this check again after each install.

  3. 03

    It gives the exact spot and the way out

    The check is on your exact version, not just the package name. For each affected package, a “What to do” line names the version to move to, and that version is itself checked before it is recommended.

  4. 04

    It never calls “all clear” in the fog

    A database that does not answer is named in the report. If the check could not be done, the verdict is “INCOMPLETE”, and the agent has to tell you.

  5. 05

    It watches beyond the trees too

    PostgreSQL, nginx, Windows Server: for what is not a package, a keyword watch brings up recent CERT-FR bulletins and vulnerabilities exploited in real attacks.

  6. 06

    It keeps watch without an agent too

    A command line for you and for your CI: vigie check on a folder or on a single package. It exits with 0 when nothing is high priority, 1 on high-priority findings, 2 when the check could not be completed. Options: --json and --fail-on.

Three commands to raise the tower

The easy way: paste the prompt and your agent does it all. If you would rather do it by hand, here are the three commands.

  1. Get Vigie

    The code lands in the ~/.vigie folder. There is nothing else to install.

    git clone --depth 1 --filter=blob:none --sparse https://github.com/Connected-Mate/vigie ~/.vigie && git -C ~/.vigie sparse-checkout set bin src

  2. See the report for your project

    Run it from your project folder: Vigie reads its dependency files and tells you what is wrong.

    node ~/.vigie/bin/vigie.mjs check .

  3. Connect Vigie to your agent

    In this project, it declares the MCP server, sets the hook and adds the rule to Claude Code’s instructions. It also exists for gemini and cursor.

    node ~/.vigie/bin/vigie.mjs setup claude

What the lookout cannot see

A lookout tower does not replace the fire crew, or looking after the forest. Here are its blind spots, stated plainly.

  • It only sees smoke that has been reported

    Vigie only knows publicly disclosed vulnerabilities in published packages. It does not find flaws in your own code, misconfiguration, or vulnerabilities nobody has reported yet. “Nothing known today” does not mean “safe”.

  • A fire lit this morning is on no map yet

    A brand-new malicious release is not in any database yet. Vigie tells you when a version is less than 3 days old; it cannot tell you it is hostile.

  • The regional bulletin only keeps recent issues

    CERT-FR only exposes its latest bulletins. The keyword watch matches product names, not your exact version: an empty answer proves nothing.

  • Without a detailed map, it only sees the forest edge

    Without a lockfile (package.json, pyproject.toml or pom.xml alone), only the versions written in the file are checked, not what they pull in. Vigie says so in the report.

  • It guards the gate, not every trail

    The hook reads shell commands: it is a guardrail, not a sandbox. An install hidden in a script (make deps, ./setup.sh) is not seen before it runs. The check after an edit and vigie check in CI are there for that.

  • In the fog, the gate stays open

    If the databases are unreachable or too slow, the hook lets the command through and says so. To block instead, set VIGIE_STRICT=1.

Frequently asked questions

Is it really free?

Yes. Vigie is free, open source (MIT license), with no account and no key. The databases it asks are public and free as well.

What exactly does Vigie check?

Known vulnerabilities in the packages your project uses, on their exact version, and malicious packages. For each vulnerability: whether it is exploited in real attacks, how likely it is to be soon, whether a CERT-FR bulletin exists, and which version to move to. When you check single packages, deps.dev adds signals that are not vulnerabilities: a deprecated version, a version published in the last 3 days.

What does Vigie not see?

Anything that is not a public vulnerability in a published package: flaws in your own code, misconfiguration, vulnerabilities not reported yet, a malicious release published a moment ago. Without a lockfile, what your dependencies pull in is not checked. An install hidden in a script gets past the hook. And CERT-FR only gives its latest bulletins. A report with no finding means “nothing known today”, not “safe”.

What leaves my machine?

The names and versions of your packages, and the public ids of the vulnerabilities found. They go to the public services Vigie asks: OSV.dev, CISA KEV, EPSS, CERT-FR, deps.dev, and the npm and PyPI registries to learn which version an install would bring. Never your code, never your file paths. Results are kept on your machine in ~/.cache/vigie, cleaned after 30 days.

Which agents does it work with?

The tools work with any MCP-compatible agent. The hook understands the events of Claude Code, Codex, Gemini CLI, Cursor, Copilot and Devin/Windsurf. To be precise: it is proven inside real Claude Code sessions; for the others, it is built from their documentation. On the machine side: tested on macOS with Node 22, written for Node 18 and later and for Windows paths, not yet run there.

Which languages are covered?

Package by package, ten ecosystems: npm, PyPI, Maven, Go, crates.io, NuGet, Packagist, RubyGems, Pub and Hex. For a project folder and its sub-folders, Vigie reads package-lock.json, npm-shrinkwrap.json, pnpm-lock.yaml, yarn.lock, bun.lock, package.json, requirements*.txt, poetry.lock, uv.lock, Pipfile.lock, pyproject.toml, Cargo.lock, go.mod, composer.lock, Gemfile.lock, gradle.lockfile, pom.xml, packages.lock.json and pubspec.lock.

What if a database is down, or slow?

The database that failed is named in the report. If an older copy exists on your machine, Vigie uses it and says so. If OSV.dev does not answer, the verdict is “INCOMPLETE”, never “all clear”. As for the hook, it never holds your agent for more than 20 seconds: past that, it lets the command through and says so, unless VIGIE_STRICT=1 is set.

The hook blocks a package I really need. What now?

That is your call. A risk you accept goes in a .vigieignore file at the project root: it stops blocking, but stays listed in every report. A malicious package cannot be accepted. And your agent is told never to edit that file for you.

How do I remove it?

In each project where you set it up, run node ~/.vigie/bin/vigie.mjs setup claude --remove (or gemini, cursor). You can then delete the ~/.vigie and ~/.cache/vigie folders. If an agent was configured by hand, remove the vigie entries and the rule you added. Your agent can do it for you.

Why “Vigie”?

“Vigie” is French for a lookout: the watch post, and the person keeping it. Like a fire lookout in a tower, the tool does not fight the fire: it spots it early and tells the crew, your agent, where to go and what to do.
